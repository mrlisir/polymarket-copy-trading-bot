# 更新日志 V5

更新时间：2026-03-21

## 本版重点

V5 主要聚焦 **`.env` 热更新**：进程运行期间可周期性重新加载项目根目录的 `.env`，将多数运行时配置写回内存中的 `ENV`，**无需重启**即可调整跟单列表、策略参数、轮询间隔等。

> **跟单回溯 + Excel 导出** 已单独记入 **`docs/更新日志_V6.md`**。

## 新增功能：`.env` 热重载（实盘 + Dry Run）

### 行为说明

- 新增环境变量 **`ENV_FILE_RELOAD_INTERVAL_MS`**（毫秒）：
  - **`0`**：关闭热重载（默认，与旧行为一致）。
  - **`> 0`**：启用；校验要求 **≥ 5000**（避免过于频繁读盘与校验）。
- 主进程在 **交易监控 + 执行器** 启动后，以 **1 秒** 为节拍检查是否到达间隔，满足则调用 **`reloadEnvFromDisk()`**：
  - 使用 `dotenv` **`override: true`** 重新读取 **`process.cwd()` 下的 `.env`**；
  - 再次执行与启动时一致的校验（必填项、地址、数值、URL 等）；
  - 校验失败则 **放弃本次重载**，打日志警告，**保留当前内存配置**。
- 成功重载后日志示例：`已从 .env 热更新配置`。

### 连接类配置：不参与热更

以下两项在进程 **首次启动** 时读入 `ENV` 后，**热重载不会改写**（避免已建立的 Mongo / 链上连接与 `ENV` 漂移）：

- **`MONGO_URI`**
- **`RPC_URL`**

若需更换数据库或 RPC，请 **重启进程**。  
（`HTTP_PROXY_BYPASS_RPC` 仍用启动时的 `ENV.RPC_URL` 解析主机名写入 `NO_PROXY`，与上述策略一致。）

### 热更后生效的典型项

包括但不限于：

- **`USER_ADDRESSES_FOLLOW` / `USER_ADDRESSES_REVERSE`**（合并列表与每位交易员的跟买/反买模式）
- **`FETCH_INTERVAL`、`RETRY_LIMIT`、跟单策略与限额、`COPY_STRATEGY_*`、订单簿缓存、滑点、聚合开关、熔断与双向锁、邮件、对账周期等**（凡 `applyReloadableProcessEnvToRuntimeEnv` 与 `mergeCopyStrategyConfig` 覆盖的字段）

### 已知限制

- **已创建的 ClobClient** 仍使用初始化时的密钥/代理钱包/CLOB 地址；若修改 **`PRIVATE_KEY` / `PROXY_WALLET` / `CLOB_*`** 等，建议 **重启进程** 以重新建连。

## 核心 API / 入口

- **`src/config/env.ts`**
  - **`reloadEnvFromDisk()`**：热重载入口；失败返回 `{ ok: false, error }`。
  - **`applyReloadableProcessEnvToRuntimeEnv()`**：可热更标量写回 `ENV`（跳过 Mongo/RPC）。
  - **`mergeCopyStrategyConfig`**：合并 `COPY_STRATEGY` 解析结果到 `ENV.COPY_STRATEGY_CONFIG`。
  - **`syncHttpProxySideEffects()`**：启动与热重载成功后同步 `HTTP(S)_PROXY` / `NO_PROXY`。
- **`src/index.ts`**（实盘）：监控与执行器启动后注册定时器，关闭时 `clearInterval`。
- **`src/dryRun.ts`**（模拟）：同上，与实盘行为一致（符合 Dry Run / 实盘配置对齐规则）。

## 注意事项

- 热重载只保证 **内存中 `ENV` 与 `process.env`（由 dotenv 覆盖部分）** 更新；Mongo 连接串、RPC、已建好的 Clob 客户端仍以 **启动时** 或 **当前连接** 为准。
- 与 V4 的「跟单列仅 FOLLOW/REVERSE」「熔断」「双向锁」等逻辑 **并存**；热更后可立即改变下一轮的跟单名单与多数策略参数。

## 补充：反买（`USER_ADDRESSES_REVERSE`）与「订单簿无卖单」

### 现象

日志出现 **`No asks available in order book`** 或 **`订单簿无卖单`**，且跟单配置为 **反买**。

### 原因（不是配置错误）

- 反买时，交易员买 **Up**，机器人会去买 **对侧 outcome 的 token（如 Down）**。
- 市价/FOK 吃单需要盘口上有 **asks（卖单）**。短时盘、5 分钟 **Up/Down** 等市场，流动性往往集中在 **热门一侧**，**对侧整条 order book 可能没有卖单**，则无法成交。
- 若同一交易员改为 **正买列**（`USER_ADDRESSES_FOLLOW`），买的是与交易员 **同一 token**，通常更容易碰到有深度的那一侧——因此容易误以为是「反买列导致坏了」，实为 **盘口结构**。

### 可选应对

| 做法 | 说明 |
|------|------|
| 继续反买 | 接受对侧常无深度；或等卖单出现后再成交 |
| 希望尽量跟单成交 | 将该地址放到 **正买列**，与交易员同腿 |
| 减少此类情况 | 优先跟 **周期更长、盘口更厚** 的市场 |

### 代码侧（V5 同期）

- 实盘 **`postOrder.ts`**、模拟 **`dryRunExecutor.ts`**：反买且无卖单时，日志会明确提示 **与 REVERSE 列配置无关**。
- 反买 **BUY** 的滑点参考价：在典型二元、价格在 (0,1) 时，用 **`1 - 交易员成交价`** 近似对侧参考价，再与 **`ORDER_PRICE_SLIPPAGE_USD`** 比较（正买仍用交易员原价）。
- **若网页有盘口但机器人报无 asks**：已对 **`token_id` 做去空白/换行规范化**、订单簿响应兼容 **`asks` / `sells`**、**asks 为空时丢弃缓存并强制再拉一次 CLOB**，并打印 **midpoint** 辅助判断是否为 token 不一致或瞬时盘口变化（见 `src/utils/clobIds.ts`、`fetchOrderBookCached` 的 `bypassCache`）。
- **自检脚本**：`npm run verify-clob-book [conditionId]` 使用 **`fetchData`** 拉 Gamma 与 CLOB **`/book`**，打印两腿 **bids/asks** 数量并校验 **`resolveReverseAssetForCondition`**（可与 polymarket.com 同一市场对照）。
- **Data API**：若 `asset` / `oppositeAsset` 被 JSON 解析成 **number**，大整数可能损坏；监控入库前使用 **`safeClobAssetFromApi`**（见 `src/utils/clobIds.ts`、`tradeMonitor.ts`）。

详见：`docs/多交易员指南.md` 中的「中文版：正买列 / 反买列与流动性」。

### 修复：Gamma `condition_id` 查询参数无效

- Polymarket Gamma 的 `/markets` 应使用 **`condition_ids`**；使用 **`condition_id`** 时参数会被忽略，接口返回与目标 condition **无关**的市场列表。
- 后果：`getConditionTokensMetaCached` / 反买对侧解析 / `fetchOppositeAsset` 等可能**拿不到正确的 `clobTokenIds`**，表现为「无 asks」、对侧错误等。
- 已把相关请求统一为 **`condition_ids=`**（`conditionTokens`、`tradeMonitor`、`dryRunExecutor`、`gammaSettlement`、`emailNotifier`）。
- 另：`getConditionTokensMetaCached` 在 **请求失败时不再写入空结果缓存**；`conditionId` 与 Gamma 返回做 **大小写不敏感**比对。
